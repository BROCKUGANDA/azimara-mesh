# 0. MISSION

Transform the existing product implementation, or build its first complete implementation if no functional repository exists, into Azimara Mesh.

Azimara Mesh is a platform through which organisations deploy, coordinate, secure, monitor, evaluate and control fleets of AI agents.

It must provide a complete operational lifecycle.

An enterprise must be able to:

1. Register and create agents.
2. Import existing agents and frameworks.
3. Configure models and providers.
4. Assign tools, APIs and integrations.
5. Define agent permissions and identities.
6. Organise agents into teams and fleets.
7. Build multi-agent workflows.
8. Deploy agents into controlled environments.
9. Execute tasks and coordinate agent communication.
10. Monitor execution in real time.
11. Trace tool calls and agent-to-agent interactions.
12. Evaluate output quality, safety and reliability.
13. Manage memory and contextual information.
14. Control autonomy and human approval requirements.
15. Manage execution budgets and resource consumption.
16. Version, test, promote and roll back agents.
17. Audit every consequential operation.
18. Measure business and operational performance.
19. Scale fleets without losing control.
20. Commercially operate the infrastructure through a subscription and consumption-based product.

This is not merely an agent builder.

It is not simply a workflow canvas.

It is not a chatbot management application.

It is the operational control plane for enterprise AI agent fleets.

The platform must remain provider-neutral, framework-neutral and deployment-flexible.

# PART I: ENGINEERING EXECUTION RULES

## 1. Repository-first engineering

Before making changes:

- Inspect the complete repository.
- Identify the current framework, languages and dependencies.
- Inspect all existing modules and architectural boundaries.
- Identify the current authentication system.
- Inspect database schemas and migrations.
- Review existing agent execution logic.
- Inspect queues, workers and scheduling.
- Review integrations and model providers.
- Inspect frontend routes and components.
- Inspect testing and deployment procedures.
- Identify production blockers.
- Determine which features already exist and are functional.

Create:

- `docs/engineering/REPOSITORY_AUDIT.md`
- `docs/engineering/CURRENT_STATE.md`
- `docs/architecture/TARGET_ARCHITECTURE.md`
- `docs/engineering/TECHNICAL_GAP_ANALYSIS.md`
- `docs/engineering/IMPLEMENTATION_ROADMAP.md`

Do not replace a working technology stack simply because another framework is fashionable.

Preserve existing useful implementations.

## 2. Engineering quality

All implementation must include:

- Strict type safety.
- Input validation.
- Consistent error contracts.
- Structured logging.
- Request correlation.
- Idempotency where appropriate.
- Explicit timeout handling.
- Classified retries.
- Graceful shutdown.
- Resource cleanup.
- Concurrency protection.
- Permission checks.
- Secure secret handling.
- Unit tests.
- Integration tests.
- Regression tests.

Avoid:

- Fake success responses.
- Hardcoded production data.
- Placeholder integrations presented as functional.
- In-memory state for durable workflows.
- Unrestricted agent permissions.
- Unbounded loops.
- Infinite agent delegation.
- Uncontrolled autonomous tool execution.
- Unvalidated external output.
- Untracked model spending.

Every feature must be verified against its actual acceptance criteria.

# PART II: PRODUCT ARCHITECTURE

## 3. Core architectural model

Build five logically separated infrastructure planes.

### 3.1 Control Plane

The central administrative and configuration system.

Responsible for:

- Organizations.
- Workspaces.
- Users.
- Agent registry.
- Agent definitions.
- Agent versions.
- Teams and fleets.
- Deployment configuration.
- Policies.
- Identity management.
- Model configuration.
- Tool registry.
- Workflow definitions.
- Approvals.
- Entitlements.
- Billing.

The control plane defines what should exist and what is permitted to run.

It must not directly execute arbitrary agent code within API request handlers.

### 3.2 Execution Plane

Runs the actual AI agents.

Responsible for:

- Runtime provisioning.
- Isolated execution.
- Workflow execution.
- Task scheduling.
- Agent coordination.
- Tool invocation.
- Resource management.
- Checkpointing.
- Recovery.
- Cancellation.
- Autoscaling.

Every execution must have bounded resources, maximum execution time, concurrency constraints and an identifiable execution identity.

### 3.3 Intelligence Plane

Responsible for model and agent intelligence services.

Components:

- Model gateway.
- Model selection.
- Model fallback.
- Prompt registry.
- Context assembly.
- Memory retrieval.
- Embedding services.
- Evaluation engine.
- Agent routing.
- Model performance analysis.

### 3.4 Trust and Governance Plane

Responsible for ensuring the other planes operate within organizational boundaries.

Components:

- Agent identity.
- Service identity.
- Authorization.
- Policy evaluation.
- Secrets brokerage.
- Data governance.
- Human approval.
- Risk evaluation.
- Audit records.
- Security analysis.

The trust plane must enforce permissions independently of the LLM.

### 3.5 Observability and Data Plane

Responsible for platform-wide visibility.

Components:

- Logs.
- Metrics.
- Distributed traces.
- Execution events.
- Audit evidence.
- Analytics.
- Evaluation history.
- Cost records.
- Data retention.

Use OpenTelemetry-compatible instrumentation.

## 4. Infrastructure architecture

Evaluate the current stack before selecting technologies.

Potential foundational components:

- PostgreSQL for transactional metadata.
- Redis for appropriate caching and ephemeral coordination.
- Object storage for artifacts, datasets and large execution outputs.
- pgvector or a dedicated vector store for semantic retrieval.
- NATS, Kafka, SQS or equivalent event infrastructure.
- Temporal, Step Functions or equivalent durable workflow orchestration.
- OpenTelemetry for telemetry.
- Isolated container or microVM execution environments.

Do not deploy every technology simply because it appears in this list.

Choose components according to workload, deployment model, operational complexity and demonstrated need.

Design for horizontal scalability and clear failure boundaries.

## 5. Multi-tenancy

Build strong organisation isolation.

Hierarchy:

Organization → Workspace → Project → Environment → Agent → Deployment → Execution.

Implement:

- Tenant-aware database access.
- Workspace boundaries.
- Project ownership.
- Environment isolation.
- Resource quotas.
- Separate secret scopes.
- Access control.
- Audit boundaries.
- Data retention.
- Usage attribution.

Cross-tenant access must be denied by default and tested explicitly.

Support multiple customer projects and independent development, staging and production environments.

- Service accounts.
- Scoped permissions.

- Identity revocation.

## 20. Permission system

Implement:

- RBAC.
- ABAC.
- Workspace permissions.
- Project permissions.
- Resource permissions.
- Agent-specific permissions.
- Tool-specific permissions.
- Environment-specific restrictions.

Separate permission to edit an agent from permission to deploy it or authorize its production operations.

## 21. Autonomy levels

Offer explicit autonomy controls.

**A0: Observe**

Read approved information and produce reports.

**A1: Recommend**

Analyze information and propose actions.

**A2: Human-approved**

Prepare operations that require authorization before execution.

**A3: Bounded autonomous**

Execute specifically approved operation classes within configured policies, resource scopes and budgets.

Default newly created production agents to conservative autonomy.

High-impact actions must require appropriate approval, regardless of how confident an LLM claims to be.

## 22. Policy engine

Evaluate:

- Agent identity.

- Autonomy level.
- Approval requirements.

Provide:

- Allow rules.
- Deny rules.
- Constraints.
- Approval rules.
- Mandatory evaluations.
- Spending policies.
- Model restrictions.
- Network restrictions.
- Data handling rules.

Policy evaluation must happen on every consequential tool invocation, not merely when an agent starts.

## 23. Human oversight

# PART XVII: FINAL DEFINITION OF DONE

The platform is not complete because a dashboard looks impressive.

The platform is complete when it can demonstrably:

1. Register and manage agents.
2. Deploy multiple agent frameworks.
3. Coordinate multi-agent workflows.
4. Enforce scoped identities and permissions.
5. Isolate execution environments.
6. Securely invoke external tools.
7. Maintain durable execution state.
8. Prevent unbounded delegation.
9. Monitor every significant execution step.
10. Evaluate agent quality and safety.
11. Manage memory and data access.
12. Control models and infrastructure spending.
13. Version and roll back agents.
14. Handle failures and provider outages.
15. Enforce human approval requirements.
16. Preserve audit evidence.
17. Isolate customer organizations.
18. Meter and bill product usage accurately.
19. Recover from tested infrastructure failures.
20. Support real customer deployments.

For every major feature, provide implementation evidence, test evidence, operational requirements and remaining limitations.

Never manufacture adoption, uptime, execution counts or evaluation scores.

Never claim production deployment without verifying the deployed environment.

Never make a policy or permission less restrictive to get a feature working.
